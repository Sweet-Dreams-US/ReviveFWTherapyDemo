# Meta Pixel — REVIVE (revivefw.com)

## Platform

Custom **static HTML/CSS/JS on Vercel**. No WordPress, no Squarespace, no CMS,
and **no tag manager** (no GTM container exists). Each page owns its own
`<head>`; the 20+ blog pages are generated by `scripts/build-blog.js`.

So the pixel is edited directly into the site — there is no plugin or app to
install, and no GTM to route through. Because there is no shared head template,
the pixel is installed as a **one-line script tag per page pointing at a single
shared file**, so the Pixel ID lives in exactly one place.

---

## ⚠️ Before this goes live: set the Pixel ID

`scripts/meta-pixel.js` line 29 currently reads:

```js
var PIXEL_ID = 'REPLACE_WITH_META_PIXEL_ID';
```

Replace it with the real ID from **Events Manager → Data Sources → Pixels**.

Until then the pixel is **inert by design**: it loads nothing from Meta, defines
no `fbq`, fires no events, and logs one console warning. Nothing breaks, and no
events land on a wrong pixel. The site is safe to deploy in this state.

The same ID must also be set as the `META_PIXEL_ID` env var in Vercel (see
Conversions API below). **If the two differ, browser and server events land on
different pixels and deduplication silently fails.**

A Pixel ID is a public identifier — it ships in the page source by design. It is
not a secret and belongs in the repo. The **CAPI access token is** the secret and
must stay in Vercel env only.

## What is installed

### Base code — `scripts/meta-pixel.js`

Loaded synchronously from the `<head>` of **every public page** (31 pages: 10
top-level + 21 blog posts), so `PageView` fires on every load, not just the
landing page. Installed via:

```html
<script src="/scripts/meta-pixel.js"></script>
```

`admin.html` is deliberately **excluded** — it is the internal operator console.
Tracking staff would pollute the audiences and the funnel numbers.

### Events

| Event | Where it fires | Notes |
|---|---|---|
| `PageView` | Every page, automatically | From the base code. |
| `ViewContent` | `/join` and `/pricing` only | Separates "saw the offer" from "saw any page". Carries `content_name` so the two are distinguishable in Events Manager. |
| `Lead` | `/join`, on the form's **success state** | Fires only after `POST /api/inquiry` returns 200. See below. |

Offer pages are configured in the `OFFER_PAGES` map in `scripts/meta-pixel.js` —
add a path there to fire `ViewContent` on it.

**Deliberately not used:** `CompleteRegistration` and `Purchase`. Neither actual
event (in-person signup, app-store install) happens on-site, so firing them here
would be inaccurate and would mislead campaign optimization.

**No `<noscript>` fallback image.** It would require hardcoding the Pixel ID a
second time on all 31 pages, creating a second source of truth for the sake of
JS-disabled visitors — who cannot use the form (or most of the site) anyway.

### The `Lead` trigger

The form is a **native HTML form**, not a third-party embed — no Typeform, no
iframe, no booking widget — so it is wired with a normal JS submit handler and
needs no redirect-to-thank-you-page workaround.

`Lead` fires in `join.html`'s submit handler, and only on a confirmed HTTP 200
from `/api/inquiry`:

- **Not** on button click, and **not** on validation pass.
- On a 4xx/5xx the visitor sees an error, the button re-enables, and **no `Lead`
  fires** — a submission that failed is not a lead, and counting it would teach
  the campaign to optimize toward failures.
- A `submitted` flag blocks double-fire from double-clicking; it resets on
  failure so a retry still works.
- Refresh and back-button do not re-fire it — `Lead` only exists inside the
  submit handler, never on load.

### Conversions API (the "stretch goal") — already built

`api/_meta.js` + `api/inquiry.js` already send a **server-side `Lead`** with
SHA-256-hashed PII, the client IP/user-agent, and the `_fbp`/`_fbc` cookies.
This was ported in previously but had no browser half to pair with.

The browser now generates an event ID, sends it as `metaEventId` in the request
body, and passes the same value to `fbq` as `eventID`. Meta sees both events with
one `event_id` and **counts them once**, taking the better match quality. Verified
locally: browser `eventID` and server `metaEventId` match exactly.

Required Vercel env vars:

| Var | Purpose |
|---|---|
| `META_PIXEL_ID` | Must equal the ID in `scripts/meta-pixel.js`. |
| `META_CAPI_TOKEN` | CAPI access token (secret — Vercel env only). |
| `META_TEST_EVENT_CODE` | Optional. Set while testing so events show in **Test Events**; **remove before launch**. |

## Verification (do this before the campaign goes live)

1. Set `PIXEL_ID` in `scripts/meta-pixel.js` and `META_PIXEL_ID` in Vercel, then
   deploy.
2. Install the **Meta Pixel Helper** Chrome extension.
3. Load `revivefw.com` — Helper shows **1 pixel, PageView**.
4. Load `revivefw.com/join` — Helper shows **PageView + ViewContent**
   (`content_name: Free Day Pass — Claim Page`).
5. Submit the form with a real address you can check. Confirm:
   - Helper shows **exactly one `Lead`**.
   - The lead arrives at `info@revivefw.com` and in the admin console.
6. **Refresh the page and press back** — confirm **no second `Lead`**.
7. In **Events Manager → Test Events**, confirm the `Lead` shows as received from
   **both** Browser and Server, deduplicated into one event.
8. Remove `META_TEST_EVENT_CODE` from Vercel.

Already verified locally against a stubbed API: PageView/ViewContent/Lead all
fire on the right pages, `Lead` fires exactly once on success, zero times on a
502, once (not three times) on a triple-click, and zero times on reload after a
successful submit.
